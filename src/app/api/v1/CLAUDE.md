# api/v1 — Route Handlers REST por papel

Camada HTTP fina: autentica, valida o corpo e delega a serviços de domínio. Sensível a segurança: é a fronteira com entrada não confiável.

## Responsibility

Pertence aqui: `route.ts` agrupados por papel (`admin/`, `teacher/`, `pedagogy/`, `agendas/`, `auth/`...), com `__tests__/route.test.ts` ao lado. NÃO pertence: regra de negócio e acesso ao Prisma (`src/domains/*/services/`), schemas Zod (`src/lib/validators/*.validator.ts`), mapeamento de erros (`src/lib/api/`) e guarda de rota por papel (`src/lib/auth/rbac.ts`, aplicada pelo `src/middleware.ts`).

## Key patterns

- Todo handler é `try { await requireUser(req, [Role.X]) ... } catch (e) { return apiError(e) }`; `requireUser` vem de `@/lib/auth/request-user`.
- Corpo: `schema.safeParse(await req.json())`; falha devolve 400 com `{ success: false, error, details }`. Exemplo: `createCourseSchema` em `admin/courses/route.ts`.
- Sucesso: `NextResponse.json({ success: true, <recurso> })`; erro: `{ success: false, error }` via `apiError`.
- Erros de domínio: serviço lança `DomainError(status, message, details?)`; `apiError` também mapeia `AuthError`, `ZodError`, `SyntaxError` (400) e Prisma P2002/P2025/P2003 (409/404/400); o resto vira 500 sem vazar detalhes.
- Rota dinâmica: `{ params }: { params: Promise<{ id: string }> }` com `await params` (ex.: `teacher/assessments/[id]/route.ts`).
- Passe o `user` retornado por `requireUser` ao serviço para checar propriedade/escopo (`updateAssessment(id, user, data)`); papel sozinho não basta.

## Local conventions

- Teste de rota: `vi.hoisted` + `vi.mock('@/lib/auth/request-user')` e do serviço; assert de `requireUser` chamado com os papéis esperados.
- Rota nova exige entrada em `PROTECTED_ROUTE_ROLES` (senão cai em negar por padrão) e, se pública, em `PUBLIC_ROUTES`.
- Mensagens ao usuário em pt-BR; nada de `console.log` de body/cookies.
